openOMSI

Privacy

Applies to the openOMSI game, launcher and project-run game services on supported platforms, including Windows, Linux, Android, iPhone, iPad and Mac. Last updated 1 November 2026.

openOMSI has no player accounts, advertising or third-party analytics SDKs. Most gameplay, settings, save files, screenshots, OMSI 2 content and diagnostics remain on your device. Some features do communicate data over the network, including the optional multiplayer features and the "Playing now" counter, which is enabled by default. This page explains the purpose, recipients, controls and known retention of those data flows. It does not cover Discord accounts, Discord servers or their bots.

1. "Playing now" counter

While you drive, the game sends a request to the project's presence service (hosted on Cloudflare) about every ten minutes. The request contains a new random session identifier generated at each start, the openOMSI version and the operating-system family (for example Windows, Linux, macOS, Android or iOS). It does not include your name, map, vehicle, hardware identifier or a list of what you do in-game. The game sends a goodbye request on exit when possible.

The service uses these data to show an approximate number of people playing, including totals by operating-system family. The service is designed not to store IP addresses; it forgets a session identifier after 25 minutes without a message. The hosting network necessarily handles connection metadata, including the source IP, when delivering requests; its own processing is separate from the game's stored counter data.

Control: Settings → General → "Count me on the website's 'playing now'". It is on by default and can be switched off. The OMSI_NO_PRESENCE=1 launch flag also disables it. Dedicated servers are not counted.

2. Multiplayer: information shared with hosts and players

If you host or join multiplayer, the game exchanges the information necessary to establish the connection and synchronize the simulation. Depending on the session this includes your chosen driver name, player/session identifiers, IP address or connection endpoint, vehicle and repaint information, position, movement, vehicle state, and game/session events. Other players and the session host may receive the data needed to display or interact with you. The host manages the session; player-hosted and third-party dedicated servers are operated by their respective owners, not necessarily by the openOMSI team.

Connections can use direct UDP, WebSockets, local networking or Cloudflare tunnels. "Connect by Code" may use STUN (including Google and Cloudflare public servers) to discover external network endpoints, UPnP to request router port forwarding, and ntfy.sh as a rendezvous relay for connection addresses. These providers can receive technical connection metadata. The rendezvous service is used to find peers, not to upload the game's simulation data.

In-game messages and actions are visible to the relevant participants and may be processed or logged by the host for administration. Hosts can use moderation and ban tools. We cannot specify one retention period for independently operated servers: ask the server operator about its logs, moderation records and retention.

3. Multiplayer machine identifier and bans

For machine bans, the client normally sends the host a 128-bit identifier derived using SHA-256 from an operating-system machine identifier (for example Windows MachineGuid, Linux machine-id or macOS IOPlatformUUID). Where one is unavailable, a locally stored random value can be used. The underlying machine identifier is not sent, and this mechanism does not read disk or motherboard serial numbers. However, the derived value is stable across sessions and shared with each server you join. Different hosts could therefore compare it; it should not be treated as anonymous.

Server owners can keep machine-ban records, including the associated name, reason and expiry, in files on their own systems. A ban can expire or persist until an administrator removes it, depending on the action taken. The game also supports server-side administration audit logs that may include names, reasons, chat or command text after filtering; these are local to the server operator and are subject to that operator's retention practices.

Control: start the game with OMSI_NO_HARDWARE_ID=1 to omit the machine identifier. A server configured to require it may then refuse the connection. See Dedicated server documentation for how bans work.

4. Multiplayer voice chat

Voice chat is off by default. When you enable it and transmit (push-to-talk, or open-microphone mode if selected), the game captures microphone audio, encodes short Opus frames and sends them through the multiplayer session to permitted listeners. Nearby voice uses player position; radio voice is session-wide. The server routes compressed frames without decoding them, and the openOMSI voice implementation does not record them to disk or log their audio content. This cannot prevent another participant or a third-party tool from recording what they hear.

Controls: Settings → Sound → Voice chat; push-to-talk or open mode; player mute controls. Mute preferences are stored locally in ~/.openomsi/voice_mutes.txt. The microphone permission is managed by your operating system. For details see Voice chat documentation.

5. Public server list, server status and shared content

A dedicated server operator may opt in to the project's public server directory. In that case the directory receives server information such as its name, description, map, connection address, version, protocol, player count and capacity; it does not receive a list of players. Listings expire about three minutes after the last heartbeat. The directory uses short-lived connection information and a source-address hash for rate limiting; the server address itself is published so players can connect.

A server can independently expose a status endpoint containing server and simulation information. If its operator enables share_positions (off by default), a separate /players endpoint can expose players' chosen names, vehicles and live in-game positions to visitors of that server endpoint. The project-wide directory does not turn this on.

Some multiplayer servers accept or supply maps, mods, vehicles and repaint files. When a server accepts player buses (the documented dedicated-server default), files used by the selected vehicle may be transferred to the host and then to other players. Hosts keep these in their own content store; the documented default for unused uploaded buses is 30 days after last use, but active/shared files and operator settings can affect this. Check content you share for information you did not intend to distribute. See Server documentation.

6. Updates, downloads and other online services

  • Updates: the launcher and game can check the openOMSI GitHub releases and download build files from GitHub. The check is enabled by default (update_check); automatic installation is a separate setting (update_auto, off by default). The app determines its platform locally to choose the correct release. Requests to GitHub expose ordinary HTTP connection data to GitHub and its delivery infrastructure.
  • Maps, mods and other files: when you choose a download, or a feature requires its associated asset, a request goes to the relevant host. Depending on the feature, this can include GitHub, the multiplayer host or another content provider. Cached files are stored locally until removed or cleaned by the application's cache management.
  • Machine translation: if enabled, missing interface translations are generated locally by a downloaded model. Model files come from Hugging Face; the text being translated is processed on your machine and translations are cached locally.
  • Real-world weather: when enabled, weather requests are made to aviationweather.gov. A dedicated server may fetch weather and distribute the resulting simulation weather to connected players.
  • Internet radio: selecting online radio connects to the chosen station/stream host, which receives the network request.
  • Hosting assistance: a game or dedicated server may download or run Cloudflare's cloudflared when tunnelling is used. Cloudflare then handles the network traffic passed through that tunnel.

External providers can process IP addresses, request metadata and other information under their own policies. We cannot promise that a third party keeps no access logs or uses the same retention period as openOMSI.

7. Local files, diagnostics and telemetry for external tools

Game settings, saved games, caches, content, screenshots and logs are stored locally (on desktop, typically in ~/.openomsi and the relevant game/content folders). Logs can contain technical errors and, depending on the event, names, paths, connection details or in-game messages. Local logs are not the same as automatic uploads. Consider reviewing any raw log before posting it publicly.

Support packages: the game/launcher can create a privacy-filtered diagnostic ZIP containing items such as app and OS versions, graphics backend, GPU/driver, rendering settings, memory and controller information, selected map/vehicle and filtered performance/log events. The package is saved on your device and not automatically submitted. You decide whether to attach it to a GitHub issue or send it to someone else. Review it before sharing.

Local telemetry.json: the game supports an interface for other programs on your computer. It writes the file only if it already exists; creating the file opts into the feed and deleting it stops writing. While active, it can update roughly twice per second with player bus position, speed, timetable progress, passenger information and AI timetable-bus data. It is a local file, not an automatic upload to the project. Another application that reads it has its own responsibilities if it transmits the contents elsewhere.

Control and deletion: disable optional online features in Settings; remove local exported ZIPs, logs or caches when no longer needed. Deleting local files cannot remove copies already shared with a multiplayer host, another player or an external provider.

8. Retention, recipients and privacy requests

There is no single retention period for every feature. The project-operated presence counter expires session IDs after 25 minutes; public server directory entries expire after approximately three minutes without an update. Local settings and files stay until you or the application remove them. Independently operated game servers determine their own log and ban retention, and may keep uploaded content as described above. Third-party providers follow their own policies.

The information described here is processed to operate requested game functions, maintain session security and moderation, provide updates and help diagnose problems when a player chooses to share a report. This explanation does not by itself establish compliance with the laws of every country, or replace any legally required controller, legal-basis or rights information. If you want to ask about information held by project-operated services or request deletion where applicable, contact the project below. For records held by another multiplayer server or a third-party platform, contact its operator.

Children

openOMSI does not knowingly seek personal information from children. Online features can still transmit the technical data explained above when used.

Contact and changes

For questions or privacy requests about the game, contact the maintainers through GitHub Issues or the openOMSI Discord. Do not post personal information, IP addresses, identifiers or diagnostic files in a public issue or channel; ask for an appropriate private contact method first.

This page will be updated when the game's actual data flows change. For implementation details, see the openOMSI source code.
